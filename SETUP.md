# PikaShot: setup and upkeep

## Publishing
- Quick way (as before): publish the project folder as it is.
- Faster, harder-to-copy way: `npm install` once, then `npm run deploy`. It shrinks and scrambles the scripts into `dist/` and publishes that.
- Every release: change `CACHE_NAME` in `serviceworker.js` (v64 -> v65 ...) so phones fetch the new files. (`npm run build` / `npm run deploy` stamp a version of their own on the published copy, a short code that changes whenever any file changes, so with those the number can never be forgotten.)
- How a new version reaches phones by itself: see "New versions reach phones by themselves" below.

## New versions reach phones by themselves
- **What was wrong:** the app is saved on the phone by its service worker (`serviceworker.js`) so it opens with no internet. A new version was downloaded in the background but then sat "waiting" until every open copy of the app was closed, and an installed app is hardly ever closed, so people ran the old version for days and only got the new one by clearing their browsing data. (Two other ways to stay behind: a release published without raising the version number, and a new version saving a stale copy of a file kept by the browser.)
- **Now:** (1) a new version takes over as soon as all its files are saved (`skipWaiting` in `install`, `clients.claim` in `activate`; a version that could not save every file never takes over, and the older one keeps working). (2) Its files are fetched straight from the server (`cache: 'reload'`), never from the browser's own saved copies. (3) The phone looks for a new version when the app opens, whenever it comes back to the front, and every 30 minutes while it stays open (`registerServiceWorker` / `_checkForUpdate` in `app.js`). (4) When a new version has taken over, the screen is still running the old code, so a **pop-up** (`#update-layer` in `index.html`: "PikaShot update. A new version is ready with the latest fixes and features. Tap Okay to update.") asks for one tap on **Okay**, which loads the new version. It appears only at a quiet moment (`_quietNow`: no box or message open, nothing being typed, no scanner, nothing being saved, sent or put together, no sales picked, not in the product picker, not signing up or logging in); otherwise it is tried again every 10 seconds, and when the app is put away or brought back. It sits above every other message and only Okay closes it: not a tap beside it, not Escape, not the Back button (Back is put back, as for other pop-ups), because the old screen must not carry on beside the new files. Once an update was started it is not offered again for a minute (no loops). (5) `npm run build` stamps the published `serviceworker.js` with a code made from all the files, so every build is a new version.
- **What Okay does first, so nothing is lost** (`_applyUpdate`): scan counts, which are kept in memory and sent in batches, are sent (up to 1.5 s); what is still on its way to the cloud gets up to 3 s to arrive (`waitForPendingWrites`, taken from the Firebase module by name from the whole module, so a library without it can never stop the app from starting); anything that has not arrived stays saved on the phone and goes later. The button then says "Updating…" and the page reloads; if the reload has not happened after 8 seconds the button works again. The page comes back where it was (the address keeps the screen), still logged in, with the same data: the products, sales and settings live in the phone's database, not in the page.
- **If the phone's database is taken over** (a later release that raises `dbVersion` in `db.js`, while another PikaShot window still runs the old code): the old window lets go of the database at once (`onversionchange`, which would otherwise hang the upgrade) and shows the pop-up immediately, even over an open box, because that window can no longer work; the new window shows "Close any other PikaShot window to finish updating." while it waits (`onblocked`).
- **People who are behind now:** nothing needs to be done for them. The next time their phone checks for a new version (when they open the app normally) it picks up this one, and from then on updates arrive by themselves. Anyone who clears their data is on the latest anyway.
- **What was tested:** the service worker file itself against a mock of the browser's worker (install saves everything with `reload`, then skipWaiting; a failed install does not; activate clears older versions but keeps the scanner library's cache, then claims; offline start and the admin exception unchanged), both as written and as built; and the page's update logic in the browser (every "not quiet" case, waiting while a box is open, the reload, the one-time message, the loop guard). The test browser cannot run a service worker, so one real update has not been watched end to end: after publishing, publish a small visible change a second time and check that an installed phone shows it within a few minutes of opening the app, without clearing anything.

## Link preview (WhatsApp, Facebook, X, Telegram)
- When the app's link is shared, the chat app fetches the page and reads the `og:` and `twitter:` tags in the `<head>` of `index.html` to build the preview: the picture `icons/share-card.png` (1200 x 630, the app's teal with the scanner icon, the name and "Track daily sales, stock and customers. For free."), a title and a line of text. Those apps do not run the page's scripts, so the tags must stay as plain text in `index.html`, and the addresses in them must be the full ones.
- The tags use `https://pika-shot.netlify.app/` (`og:url`, `og:image`, `twitter:image`). If the app ever moves to another address, change those three.
- To change the picture, replace `icons/share-card.png` with any 1200 x 630 picture under 300 KB (WhatsApp skips larger ones). It sits in `icons/`, so the build copies it into `dist/` by itself. Nothing about the preview needs a cache version change: only those apps' crawlers read it, never the installed app.
- After publishing: chat apps remember what they saw for a link for several days. To see the new preview at once, share the link with something added, for example `https://pika-shot.netlify.app/?v=2` (it opens the same app). Facebook and Instagram can also be told to look again at https://developers.facebook.com/tools/debug/ ("Scrape again").

## Firebase console, once
1. **Rules**: paste `firestore.rules` into Firestore Database > Rules > Publish.
2. **App Check** (stops copies of the app from using your database):
   Build > App Check > register the web app with reCAPTCHA v3 > paste the site key into `config.js` > publish.
   Set the token lifetime to 7 days (fewer reCAPTCHA checks). Watch the request graph for a few days, until nearly all
   requests show as verified, and only then press Enforce for Cloud Firestore (older cached copies of the app have no token).
3. **API key** (Google Cloud console > APIs & Services > Credentials > the browser key):
   Application restriction: websites, only your live address (`https://yourdomain/*`) and `https://pika-shot.firebaseapp.com/*`.
   API restriction: Identity Toolkit, Token Service, Cloud Firestore, Firebase App Check.
4. **Authentication > Settings > Authorized domains**: keep only your live address and the `firebaseapp.com` one.
   **Sign-in method**: only Anonymous (phones) and Email/Password (the dashboard sign-in).
5. **Index for salespeople** (optional, saves reads): Firestore > Indexes > Composite: collection `sales`,
   fields `recordedBy` ascending + `lastUpdate` ascending, scope Collection. Without it a salesperson's phone still works, it just re-reads their own sales.

## Free-plan quota (Spark: 50,000 reads and 20,000 writes a day)
- Phones only ask for what changed since last time (`lastUpdate`), and keep a copy of it on the phone, so a normal day is small.
- Where to watch: Firestore Database > Usage.
- A new phone (or cleared data) reads that account's products and sales in full once.

## Creating an account (why someone could look "new" when they come back)
- Logging in asks the server whether `users/<phone>` exists; if not, the person is treated as new and gets the WhatsApp check. So an account that never reached the server looks like a new person next time.
- It used to be possible: the sign-up sent the new account without waiting for the answer, and the server refuses it when the WhatsApp confirmation is more than an hour old *on the server* (rule `signupVerified`). The phone counted its hour from when it noticed the confirmation, which can be later, so a slow sign-up passed on the phone and was refused online, with no message. The person used the app, and later was asked to verify as a brand-new user.
- Now (`handleRegistration`, `DB.createAccount`): the server is asked first whether the confirmation still counts (3 minutes of margin kept back); the account is kept on the phone only after the server says yes (20 seconds at most, then "Check your internet and try again"); if the server refuses, the person is told the number check expired and the WhatsApp check starts again at once, before they have used the app. The phone's one-hour clock now runs from the dashboard's confirmation time (`_phoneVerified`).
- Accounts made before this change that never reached the server cannot be repaired by the app (the rules need a fresh WhatsApp check to create an account). Their owner verifies once more and fills Create account again; their products and sales are still online under the same number and come back. To count them: a number that has `products` or `sales` under `users/<phone>` but no `users/<phone>` document.

## The app icon
- A white scanner frame around a barcode on PikaShot teal (`#008C95`, the same teal as `background_color` in `manifest.json`). Because the colours match, the start-up screen Android draws on installed phones shows only the white mark on teal. That screen is made by Android from the manifest (name, `background_color`, icon): it cannot be switched off, only changed here.
- `icons/icon-192.png` and `icon-512.png` are the normal icon (rounded corners); `icon-maskable-512.png` is the full-square version that phones which cut icons into circles or squircles use. The same `icon-192.png` is the picture shown for a product that has no photo.
- An already installed app updates its icon on its own after Chrome next checks the manifest (it can take a day or more). Uninstalling and installing again shows it at once.

## Product pictures
The full photo lives on the phone. A small thumbnail (a few KB) is saved with the product in Firestore, so after logging out,
clearing browsing data or switching phones the picture comes back from the thumbnail. No Storage bucket is used.

### Snap image (`capturePhoto` in `camera.js`)
- The screen says "Opening camera..." while the camera starts, then "Snapping Image" with a 2, 1 count. The time to settle focus and brightness (`PHOTO_SETTLE_MS`, 2 seconds) counts from the moment pictures are really coming in, not from the tap, so a slow phone is no longer made to wait for its own start-up plus a full countdown on top.
- The light comes on for photos (unless the person switched it off). The shot waits a moment after it comes on (`PHOTO_LIGHT_SETTLE_MS`) so the picture is not blown out, but never waits for a light a phone does not have.
- A camera that freezes right after starting is opened once more instead of being photographed frozen. A picture that comes out empty now says so ("The picture did not come out") instead of silently doing nothing.
- Leaving the camera screen in any way (Cancel, the arrow, the phone's Back) turns the camera off at once (`showView`). Before, Back and the arrow left it running, which kept it busy for the next scan or photo and could pop up a picture after the person had left.
- Pictures are never bigger than `PHOTO_MAX_SIDE` (1280 px) on the long side.

## Things are recorded once
- A sale gets its id when the confirm box opens, and the sale plus the stock it takes out are saved together on the phone (`DB.recordSale`). A second tap, a retry or a slow connection is the same sale: if that id is already saved, nothing changes. Editing a sale moves the stock by the difference only (`DB.editSale`).
- Nothing that needs the internet (the copy of a credit sale sent to the customer, telling a supplier the stock left) holds the screen or runs before the sale is safe. The credit copy has the id `xfer_<sale id>`, so it can only exist once.
- New products keep one id for as long as the form is open. A transfer being sent keeps one id (`xfer_<key>`) for as long as its box is open and is never written over once it exists.
- Accepting a transfer adds the items once: the phone notes it (`applied:<id>`) and the transfer in the cloud gets `appliedAt`. If an earlier try claimed it but stopped before adding the items, trying again finishes the job.
- Buttons that save go through `_once(name, job, button)` in `app.js`: while one is running a second tap does nothing and the button is off.

## Profile messages (`nudges.js`)
- The one message in the Profile card comes from `nudges.js`. All the words, and when each one applies, are in the `CATALOG` list at the top of that file.
- Three kinds take turns, never the same kind twice in a row: free airtime, business insights, motivation (light Pidgin is only used in motivation).
- It changes after every 5 actions (sales, scans, transfers, receipts shared or printed, in any mix). Each person gets their own shuffled order.
- Keep each message to 8 words or fewer with one emoji, in plain words.
- When a new message arrives by itself (the 5th action, a welcome, or a nudge on app open) the menu (hamburger) button gets a warm dot and its three lines ripple for 30 seconds.
  The dot stays until the Profile is opened.
- A soft double beep goes with it, in two strengths (`_playNudgeChime` in `app.js`; the numbers are in one place if you want them louder or quieter):
  - **Important** messages beep clearly: money owed, stock running out or customers short, "Need money for stock", a win (a record day, a customer paying back) and the welcome
    (`chime: true` in `CATALOG`, about 1 message in 5; the receipt of an accepted transfer is one too). At most 4 a day, at least 15 minutes after the last important one.
  - **All the other** messages (tips, encouragement) beep about 5 times softer (14 dB down). At most 6 a day, at least 10 minutes after the last beep of any kind, so a quiet one never follows an important one closely.
  - An important beep is never held back by quiet ones. Both wait until the person is out of the scanner (so they never sit on top of scan beeps; if both kinds are waiting, the important one plays),
    and neither plays, nor is counted, if the phone has not been touched since the app opened (browsers do not allow sound before a tap).
- These change straight away instead of waiting for 5 actions: a kind nudge when the app opens after a day or more without a sale, the welcome after a first sale,
  a credit reminder (below) when the app opens, and the receipt of a transfer that was just accepted (4 seconds after it, then 3 more times that day: see Accepted transfers).

**Things people can act on** (they go first, but never two insights in a row, and not while someone is serving customers: 4 or more sales in the last half hour)
- A customer owes on credit: after 3 days unpaid, "{name} owes {amount} since {day}", then again every 3 days until "Fully repaid?" is pressed (each customer has their own 3 days, the biggest debt first, never late at night).
  A tap opens Customers at that credit card. When the app opens and a reminder is due, it is said then (once a day).
- "You're running low on {product}" (best seller first, each product at most every 2 days), and "{product} is out of stock. Restock soon" (only for products that sold in the last 30 days). A tap opens My products on the Low stock or Out of stock tab, at that product.
- Wholesalers and their salespeople: "{customer} is low on / out of {product}" (nothing left first, each customer at most every 3 days), and "{n} customers need stock" when 3 or more are low. A tap opens Customers at that customer. (A salesperson hears only about their own customers: see Salespeople and customers.)
  "Low" means under 10 units, the same line where the customer card turns red.
- "Need money for stock? Get help" is shown (at most once every 3 days) to anyone with more than 4 products low or out of stock, and to a top seller whose sales fell: 3 of the 7 days before had 100+ sales, yesterday and the day before were each under 50, and more than 2 products have been low or out of stock for more than 2 days. Tapping it opens Pika's WhatsApp line (`WA_NUMBER` in `app.js`) with the words "I'm a PikaShot top seller and need money for stock."

**How the rest is chosen** (weights in `CATALOG` and `kindWeight` in `nudges.js`)
- New accounts (first week, or under 15 sales) hear more about how to earn; a slow day or a long break gets more encouragement; a fresh win (a record day, a customer paying back, 15+ sales) gets celebrated first.
- Closer to a goal counts for more (5 sales from 100, "tomorrow makes 7 days in a row"); a streak about to break says so; evenings give the day's summary; Mondays and the start of a month give a fresh-start message.
- The more often a message has been shown the less often it comes up, and the last 8 are not repeated straight away.
- "Request item transfer when you restock" is for wholesalers and retailers (not salespeople) and comes up more when stock is low.
- Customers' stock for these messages is kept on the phone (`pika_custstock_<business phone>`; a salesperson's own list is `pika_custstock_<business phone>_<their phone>`), refreshed whenever the Customers tab is open and, in the background, at most every 12 hours when the app opens (one read of that business's customer list for a wholesaler; for a salesperson only their own customers, one by one). Anything older than 3 days is ignored.

## Sounds (all made in `app.js`, no sound files)
- Good scan: one short, soft blip (`_playScanBeep`): a pure E6 with a faint octave below for warmth and above for sparkle, starting gently and fading smoothly. It replaced a sharp 2300 Hz square-wave beep.
- Transfer accepted: a rising four-note chime (`_playTransferChime`).
- New profile message: the double beep described above (`_playNudgeChime`).
- To change how a sound feels, edit the notes in its function: `freq` (pitch), `vol` (loudness), `attack` (how gently it starts) and `release` (how long it fades).

## The phone's Back button
- A modal has a step of its own in the browser's history, so Back closes it (by pressing its own Close / Cancel button, so anything waiting on it, such as a PIN prompt, is let go) instead of leaving the page. A message or question pop-up closes on Back too, and nothing behind it moves.
- Back with nothing open goes to the page before, as it always did. A modal that can not be closed (a salesperson waiting to be confirmed) lets Back go on past it.
- When adding a modal: give its Close / Cancel button a `data-back` attribute (in `index.html`), and open and close it with `showModal` / `hideModal`. In code, use `this._back()` instead of `history.back()`.
- Every Cancel and Close button has the class `btn-cancel` (a red line and red text, like Logout; over the camera it keeps a white fill so it can be read). Add `btn-cancel` to the next one too. Other buttons (Decline, Done, OK, Try Again) keep their own look.

## Salespeople and customers
- **A salesperson sees only their own customers.** A customer is theirs once they accepted something this salesperson transferred (the sale is marked `transferredTo` on the salesperson's own sales). Their Customers tab lists the credit they recorded plus the read-only stock cards of those customers, and a credit card shows "Their stock" only for such a customer. The business's other customers are never read (one document per customer is fetched, not the whole list), never shown, and never named in their messages. The list is read again as soon as a new customer of theirs appears, otherwise reused for 10 minutes (Refresh reads it again).
- **The Customers tab's empty message is the same for every kind of account** (store owner, retailer, salesperson): "Customers you transfer items to, and others who bought on credit show here." It shows while there is no customer who accepted a transfer and no unpaid credit sale (`_drawCustomers` in `app.js`). The Salespeople tab (admins only) says "No salespeople yet. Tap the + button to add one."
- **The Add a salesperson box** opens with "What a salesperson can do" and its 3 short lines first, then the phone number. The number box is not focused when the box opens (a keypad would cover the lines before they are read); they tap it when ready. The lines are never folded away: with the keypad up they simply scroll up out of the way (and back), and the box scrolls the number into view. The Cancel / Get code buttons sit in a footer that never scrolls, so both stay in view above the keypad (even on a very short screen). For a retailer the transfer line reads "Cannot transfer items." (The code's 20-minute life is shown on the next screen, beside the code.)
- **Removing a salesperson** asks for the admin's PIN in a box that says what it is for: the title is "Remove John as salesperson?" (first name), and under it: "John will be logged out right away. Their daily sales cards will be gone, so confirm any money you received first. Their sales stay in your records." (`removeSalesperson` in `app.js`; true to what it does: only the salesperson's link is deleted, so they are logged out at once and their cards leave the Salespeople tab, while the sales they recorded stay in the business's own records.) `requestPin(message, title)` takes an optional title; the other PIN questions (confirming money received, deleting a product, "fully repaid") pass none and keep "Enter your PIN" (the title is set again on every call, so one question's title never stays on the next).
- **Everyone edits only their own sales.** A sale a salesperson records carries their phone (`recordedBy`); the business's own sales carry none. `_isMySale` / `isSaleEditable` in `app.js` allow an edit (once, within 45 minutes, as before) only on a sale the signed-in person recorded: an admin sees a salesperson's sales (and can send them, and confirm their money) but gets no Edit button on them (the receding line still shows on a salesperson's sale for as long as it is new enough, for everyone who sees it: it tells how recent the sale is; `_inEditWindow`), and a salesperson's Edit button is only for sales that carry their own phone. The Confirm sale box also refuses to save an edit of someone else's sale ("Only Tunde can edit this sale.") in case one was left open. Like the rest of this section it is enforced in the app, not in the rules.
- This is enforced in the app, as the rest of what a salesperson may see is: the Firestore rules treat every signed-in phone alike (they cannot tell a salesperson from an admin), so the rules were not changed.
- **A salesperson transfers like a wholesaler.** The Transfer button shows for them when their business is a wholesaler (or the business type is not known); a salesperson of a retailer has none, as a retailer has none. The transfer is sent as the business (`senderId`, `senderStore`) with `sentBy` / `sentByName` saying which salesperson sent it, and the customer who accepts becomes that salesperson's customer.
- **A salesperson does not choose a business name or a business location when signing up.** Both come from their admin: each time the salesperson's phone checks its link it reads the admin's account (`users/<admin>.business` and `.location`), so they are always the admin's current ones (an older link that holds no name is no problem). If the admin cannot be reached just then, what the phone already knows is kept. They are kept on the salesperson's phone only (`LOCAL_ONLY_USER_FIELDS` in `db.js`), so the salesperson's own account keeps an empty business and location. The profile, receipts (on screen, printed and the shared picture) and the share-receipt text use them (`_shop()` in `app.js`), and so does the "From" on a transfer a salesperson sends.

## Wording: sentence case, and "See previous sales"
- Every label, title and button is written in sentence case: only the first word has a capital ("My shop", "My products", "All sales", "Today's sales", "Items sold", "Record sale", "Add new product", "Save product", "Confirm sale", "Welcome back!", "Create account", "Try again", "Out of stock", "Previously transferred", "Customers & salespeople"...). Names stay as names (PikaShot, WhatsApp, Lagos Island, the example names in the boxes), and a button named inside a sentence keeps its capital ("Tap Try again"). Keep new words this way. The small ALL-CAPS labels on receipts and cards are a style (`text-transform: uppercase`), not wording. The admin dashboard (`admin.html`) was not part of this.
- A sale made with no customer picked is named "Walk-in customer" (it is kept inside the sale). Sales saved earlier say "Walk-in Customer": the check that leaves walk-ins out of a customer list ignores capitals, so both are recognised.
- The home page button for earlier days says **See previous sales**. From the third sale of a day the page is given the height of a six-sale day so it scrolls comfortably; that extra room is a spacer *below* the button (`#sales-spacer`, set in `updateDashboard`), so the button always sits right under the sales that are there (16 px below the last one) and the page is as tall as it was.

## Launch check (records, transfers, loopholes, first use)
**After this release, publish `firestore.rules` again** (Firebase console > Firestore Database > Rules): an account's type and number can no longer be changed by anyone, a salesperson code is stamped by the server (it cannot be made to last longer), and a salesperson link must be for the phone it names.
- **The online clock.** A sale is stamped with the online time, and a sale's 45-minute edit window is counted on it. The time comes from the web server's own `Date` header (a HEAD request for `manifest.json`: free, no database read), asked when the app opens, whenever it comes back to the front, and right before a sale is confirmed or an edit is opened or saved (`_measureClock`, `_serverNow`). A phone whose clock is hours, days or years off (cheap phones reset after a flat battery) still puts every sale on the right day; turning the clock back no longer reopens an old sale for editing. "Today" on the home page, All sales and the salesperson cards use the same clock (`DB.now`), and a sale stamped in the future is never "today" twice. The service worker leaves anything that is not a GET to the network.
- **Sync never removes a record on its own.** The live listeners ignore "removed" (a record written again here leaves the "changed since" window for a moment while it waits for the server's time; it used to be deleted from the phone, products vanished and lost their full picture). Deleting a product travels as `deleted: true`, as before. A sync that lands after logging out is thrown away (it can never fill the next account on a shared phone), the daily product check never deletes on the word of the phone's own saved copy (no internet), and a half-written cloud record (no name, or no time) is skipped instead of stopping the sync.
- **Sales.** A sale whose product left the phone while the box was open is not recorded ("This product is no longer available."), so no sale is ever saved without its stock. An edit is checked again on the sale as it is stored when Save is tapped (transferred, money confirmed or out of time meanwhile: "This sale can no longer be edited."), only the edited fields go online (a "money confirmed" set by the admin's phone meanwhile is never undone), and the sale keeps `original` (quantity, total, discount, type, customer before the edit) and `editedAt`. Confirming a salesperson's money keeps `confirmedTotal` on each sale.
- **Product stock changed by hand** goes online as "+/- the change" (a sale on another phone while the Edit box was open stays counted), each hand change is kept in `stockEdits` (last 10: when, from, to), and lowering stock asks for the PIN ("Lower the stock?"). Price above ₦100,000,000 or stock above 1,000,000 is refused; names are at most 60 characters (people's names 40).
- **Credit sales.** The customer is picked from the phone's contacts, or typed in PikaShot's own box (name and number; the browser's prompt is gone). Numbers are kept as 11 digits (`+234 803...` becomes `0803...`). The automatic copy goes only to a number that is a PikaShot shop (not this phone, not the business, not a salesperson), checked online first; otherwise no copy is sent and the sale is free to edit. Receipts and transfers show a credit marked "Fully repaid" as paid, with nothing due.
- **Sending a transfer.** Sales of one product at different prices go as separate lines, each at its real price. An earlier offer of the same sales that nobody accepted (a credit sale's automatic copy, or a transfer to someone else) is withdrawn first (`voided`) so it can never make this one fail; if one was already accepted, the sender is told and nothing is sent. An empty selection is never sent. A waiting mark says who sent it and from which phone (`by`, `device`): only that phone frees it after 5 minutes if the server never got it; any other phone waits a day. A withdrawn transfer frees its sales on the sender's phones. An accepted sale keeps `transferredBy`: a salesperson's "Transfers" row and their customers count only accepted transfers they sent themselves (not the admin's, not ones still waiting).
- **Accepting a transfer.** Only transfers that exist online can be accepted (old-style codes that held the whole transfer are no longer read: anyone could make one and use it again and again), only by the person (or business) it was sent to, and only when every item has a name, a count above 0 and a price of 0 or more. Only the phone that claimed a transfer can finish adding it (`claimedDevice`): a second phone of the same account never adds the stock again; an accept that was interrupted after claiming finishes on the next open (`claiming` note). A received item joins a product with the same name only when one of them has no barcode (a different barcode is a different product). The supplier's view of a customer's stock is written as a map (a name with a dot or slash, like "Eva water 1.5L", stays one name), keeps one line when a product's name changes, and loses the line when the product is deleted.
- **Salespeople.** A salesperson who was removed (or left) while some money was not confirmed stays on the Salespeople tab ("no longer your salesperson", no remove button) with the same "I received the money" button until every day is confirmed. The removal box says so. A new account spends its WhatsApp check at once (nobody can set a PIN with it for the rest of the hour).
- **First use.** A blocked or missing camera no longer keeps a new user on the camera screen (they go in; each scan explains it). Opening the app with no internet the first time no longer breaks sign-up once the internet is back. Back after logging out does nothing; Back with sales picked lets go of them; "Select from products" takes the scanner's place in the history (Back never shows a dead scanner). Offline is said before a scan for a sale or a product, not after the typing. A scanner reader that failed to load once is tried again. A timed-out scan says "No barcode seen" (not "Not found"); a sale scan of a barcode the shop does not have offers the owner **Add as new product**. Scanning a product already added offers **Open**. Saving a product says "Product saved." (the first one: "Saved. Tap Record sale when you sell it."). A new product starts on the last unit used. Product cards show the whole name on up to two lines. The first-product tip is not shown to salespeople, a waiting salesperson reads "Ask your admin to add your number (0907...) as a salesperson for their store. Then enter the 4-digit code they give you here." (`_showWaiting`), and empty pages say what to tap.
- **Not changed (decide later):** credit repaid later is not added to any day's total (a credit sale's total is what was paid at the time); a salesperson's discounts have no limit; the "Copy PIN" buttons stay; two of the owner's phones could each edit the same sale in the same minute; and the rules still let any signed-in phone read and write any business's records (real accounts per person need a server: Cloud Functions on the Blaze plan).

## Confirm sale: a sale is what it says it is
- The Confirm sale box (`_processSale` in `app.js`) refuses, with a message and a shake of the box that needs fixing, a sale that does not match its type:
  - **Discount** with no amount, or 0: "Enter how much to take off. For no discount, slide the switch to the middle." (A sale used to be saved as "discount" with a discount of 0, and showed the Discounted label.) A discount more than the total is refused too. While typing, the amount is held at the total and the box shakes (as the credit part payment already was); the total can reach ₦0 (everything off), which is allowed.
  - **Credit**: nobody picked, no part payment typed (0 is fine: "Enter 0 if nothing"), more than the total, and now also **the whole total** ("They paid everything, so nothing is owing...": a credit sale needs something still owing).
  - **A product with no price** (older products saved at ₦0) cannot be sold: "Add its price in My products first." And a product can no longer be saved at ₦0: the price box needs more than 0 (an empty box, a 0 or letters all count as no price).
- A minus sign typed on a keyboard into the price, discount or part payment boxes is dropped (an amount is never below 0). While the quantity box is empty for a moment (they are typing a new number) the discount or part payment they typed stays; it is only held at the total once a quantity is there.
- Sales saved the old way as "discount" with no amount are shown and edited as ordinary sales (no Discounted label; the Edit sale box opens on the middle position). Nothing stored was changed.

## Laptop and desktop screens: two halves (like WhatsApp Web)
- On a screen at least 900 px wide and 560 px tall, the shop stays open in the **left half** (home page, bottom bar with Shop / Record sale / Products) and whatever is tapped on it opens in the **right half**: Products, All sales (from the two cards or "See all" / "See previous sales"), Customers & salespeople, and the scanner. While nothing is open there, the right half says "Tap a card or a button on the left. It opens here." (`#pane-empty`). It is only a layout: every page, button and flow is the same one a phone uses. The tall-enough rule keeps a big phone turned sideways on the phone layout; a phone is never split. Nothing was changed for any screen below that size (the layout was measured before and after at 390x760, 360x640, 844x390, 899x800 and 1024x500: identical).
- The left half is `min(50vw, 600px)` wide (`--split-left` in `style.css`: the home page was never wider than 600 px). Every rule is inside one `@media (min-width: 900px) and (min-height: 560px)` block at the end of `style.css`, under `.app-container.in-app`. `showView` sets `data-view` (the open page) and the `in-app` class (the shop is showing, not a sign-in screen) on `#app-container`; `_isSplit()` in `app.js` asks the same question in code.
- The header is one bar over both halves: "My shop" and the menu button over the left, the open page's title over the right with a close button (X, the same button as the phone's back arrow) at its left edge. Titles come from `updateHeader` as before; "All sales" keeps its filter arrow. **X** (and **Esc**, when nothing else is open and no box is being typed in) closes the page and leaves the shop alone (`_closePage`): on a phone it is Back, but here Back could show another page (one opened from the shop, then another from that page). Choosing a product for a sale ("Select a product") still goes back to the scanner. Esc also cancels a selection of sales first.
- The sales selection bar (Cancel / Edit / Receipt & transfer) sits under the half the selected sale is in (`on-right` on `#receipt-actions`). The + buttons sit at the bottom right of the page they belong to. The scanner fills the right half and the left half is dimmed and does nothing until the scan is cancelled or done (as a phone's whole screen would be). The offline banner stays over the left half. Boxes (product, sale, receipt, profile), messages, the update pop-up and the toast stay in the middle of the whole window.
- On a very wide screen the page on the right keeps a readable width (at most 860 px, in the middle of its half). Mouse users get a pointer cursor and a light hover on the bar's buttons.

## Units, cartons and the Edit product box
- **A carton is just a unit now.** The "what is inside / how many per carton" step is gone (its box, the "= 72 sachets" line on incoming transfers, the sub-unit details sent with a transfer, and a retailer's automatic carton-to-pieces conversion). Older products still hold the old sub-unit fields; nothing reads them.
- **The unit list has a small picture beside every unit** (sachet, bottle, can, tin, packet, carton; "pieces" is no longer a choice). The hidden `<select id="product-unit">` is still the real field: the button and picture list (`_initUnitPicker` in `app.js`, `.unit-*` in `style.css`) only show and set it. Pictures are the `UNIT_ICONS` in `app.js`: add one there when a unit is added to the select.
- **The unit list floats; the product box never changes when it opens.** It is one vertical list that sits in the modal layer (`#unit-menu`, the first child of `#modal-container`), outside the form, so the Add / Edit box does not grow, scroll or move whatever the list does (it used to sit inside the form and push everything down). `_placeUnitMenu` in `app.js` puts it under the Unit field with the left edges together; it is only as wide as its units (`width: max-content`, never narrower than the field), and it opens upwards when there is no room below (a very short screen: it scrolls inside itself). It follows the field if the box scrolls or the screen changes size, closes on a tap anywhere else, on Escape, on the Unit field again or after choosing, fades in and out quickly, and is dropped at once whenever any box is shown or hidden (so it never stays on screen over another box). Kept small: 18 px picture in the field, 20 px in the list, 36 px rows, 0.92rem text; with the list closed the Add and Edit boxes measure exactly what they did before the pictures. Arrow keys move through it, Enter chooses. While it is open the "Packet or Sachet?" question steps aside and comes back if the list is closed without choosing.
- **"Pieces" is no longer a unit.** It is out of the list (and out of `UNIT_LABELS`' choices). A product already saved in pieces still shows as Pieces with its picture in its Edit box (and in the list, only while it is the chosen one, so it can be seen and changed); saving it unchanged keeps `pieces`. A transfer item whose product is gone is sent in the sale's own unit, or packets, instead of "pieces".
- **"Tubs" became "Tins".** The unit saved is now `tins`. A product saved earlier as `tubs` is shown as Tins in its Edit box (`_unitName` / `_unitKey` in `app.js` treat `tubs` as `tins`, so a transfer from an older phone does not trigger the "Tin or Tin?" question) and is saved as `tins` the next time it is saved. Until then its stock line on the product card and the sale screen still say "tubs"; old sales keep the word they were made with.
- **The product box keeps Cancel and Save in view above the phone's keypad.** Like Add a salesperson, it is a scrolling top (`.pf-scroll`: the title, the delete button, the barcode, the "Stock only visible" line and the fields) and a footer (`.pf-footer`: Cancel, Save product) that never scrolls; the form (`.pf-form`) holds both, so Save is still a plain submit button. With the keypad up the box shrinks to what is left of the screen (`_followKeyboard`), the top scrolls (the title and barcode go up out of the way, the field being typed in is brought to the middle) and both buttons stay in view; a soft edge shows above them while something is hidden beneath (`more`, set by `_watchProductScroll`). The box always opens at its top (`_productBoxToTop`). The Delete button moved inside the form, so it is `type="button"`. **Without the keypad the box looks exactly as it did**: every part measures the same (Add and Edit, 390 x 760, 360 x 640 and 320 x 568), because the space all round, between the last field and the buttons (22 + 12 + 12) and between the title and the first field (the title's space below and the first field's space above add up, as they always did: `.pf-body`) were kept, including the narrow-phone rule (16 px all round at 360 px wide or less) and the short-screen rule (16 px top and bottom at 520 px high or less). If either of those two rules for boxes in `style.css` ever changes, change the matching lines for `#product-form-modal .pf-scroll` / `.pf-footer` too. The unit list follows the Unit field when the top scrolls.
- **The trash icon in the product box is small:** a 30 px circle with a 16 px symbol (the size of the pencil on the product cards), top right; the 44 px area around it that takes the tap cannot be seen (`.delete-btn-icon::after`). It was 40 px with a 28 px symbol.
- **The gap above "Product name"** (22 px) used to come from an empty block that held the Scan Barcode button; with that block gone it is `#product-name-group { margin-top: 22px }`, so the Add and Edit boxes look as they did, whether or not the barcode and "Stock only visible to last supplier" lines are above it. That line keeps its original small size; on a narrow phone it breaks evenly (`text-wrap: balance`).
- **A received item counted in a different unit** (you keep Milo in packets, sachets arrive): the stock is added as before and the product is marked `unitToConfirm`. When its Edit box is opened, a small floating question points at the Unit field: "Packet or Sachet?". Tapping one sets the field; saving settles it (the mark is cleared, and it does not use up one of the five hand edits an hour). Closing the box without saving asks again next time. Nothing is converted: the stock number is not changed. Salespeople are not asked (they cannot edit products).
- **No barcode prompts in Edit product.** A product cannot be added without a barcode, so "needs a barcode / Scan Barcode / No barcode assigned" are gone. Older products flagged "barcode-and-price" are treated as "price".

## Accepted transfers: receipt and sender
- **The receipt is not saved by itself.** A phone only lets a page save a file after a tap, so accepting a transfer now sets up a message instead (a primary nudge, `tx-receipt` in `nudges.js`): 4 seconds after the transfer is accepted it comes up in the Profile card with the menu dot, the ripple and the loud beep ("Mama Put transfer accepted. Tap to download. 🧾"), and a tap draws the receipt (the way the sender's own receipt is) and saves it as `pikashot-receipt-<store>-<date>.png`. It comes back 3 more times within the same 24 hours (90 minutes, 4 hours and 9 hours after the transfer: `RECEIPT_AT`), with different words each time, until it is downloaded; a time that went by while the app was closed comes up once, not all together, and a reminder waits while sales are coming in (the first one never waits). After 24 hours it stops. It is checked once a minute while the app is open and whenever the app opens or comes back (`_nudgeReceipts` in `app.js`).
  What the receipt needs (the items, prices, sender, time; no pictures) is kept on the phone in `pika_xfer_receipt_<phone>` until it is downloaded or the day is over; the nudge's own record is `receipt` in the person's nudge state. Only the latest accepted transfer is followed: accepting another one replaces it.
- A transfer now carries the sender's area (`senderLocation`, the LGA). "Incoming item transfer" shows it beside the phone number ("08030000001 · Surulere"). A transfer sent before this change has none: the app reads the sender's account for it.

## Sending a transfer: never "failed" when it went, and "Transferred" always shows
- **What was wrong:** the sender's phone sent the transfer first and only then marked the sales as "waiting for this person" (`pendingTransfer`), and any problem after the transfer reached the server (a read that failed, a screen that threw, the app closed, the phone switched off) both said "The transfer did not go through" and left the sales unmarked, so "Transferred" never appeared once the buyer accepted. A "failed" transfer that was tried again also became a second transfer.
- **Now, `_sendTransfer` in `app.js`:** (1) the sales are marked waiting on this phone first (`_markTransferPending`, with the time); (2) the transfer is written, and only a refusal from the server counts as "did not go through" (the marks are removed again, `_unmarkTransferPending`); a line too slow to answer within 15 seconds (`SEND_WAIT_MS`) is not a failure: the phone keeps the write and sends it when the internet is back, the person is told "Saved. The transfer will be sent as soon as your internet is back.", and a refusal that comes later frees the sales and tells them then; (3) once the server has it (or is certain to), every later step (the nudge count, closing the box, the screens, watching for the buyer) is on its own and can only be logged, never turn the transfer into a "failed". The check read after the write is gone (the write being confirmed is the check).
- **Marks that never became a transfer** (the app was closed between step 1 and step 2, or the server refused a credit sale's copy): when a marked sale's transfer is still unknown to the server (the watcher in `watchPendingTransfers` sees no document that is not just a local copy or a write still waiting) and the mark is older than 5 minutes (`PENDING_GRACE_MS`), the mark is removed (`_dropStalePending`), so the sale can be edited or transferred again instead of staying locked. A transfer that is being sent from this phone right now is never touched.
- A number changed after an earlier try that did arrive makes a new transfer (a new id) instead of reusing the old one.

## New arrivals on "My products"
- An item just accepted (a new product, or stock added to one the owner already has) is stamped `freshAt` (the accept time; the transfer's first item a millisecond later than the second, so it ranks higher). While it is set, the product sits on top of "My products", newest arrival first, and its card carries a label: **New: Add price** if it still needs a price (`needsSetup`), otherwise **New stock**.
- **Opening the product is all it takes** for it to stop being new: whether the owner then saves, changes something and saves, or just closes the box. `handleEditProduct` calls `_markSeen`, which sets `freshAt` to null on this phone and in the cloud (`DB.patchProduct`, only that field) and draws the list again, so the label is gone and the product is back in its normal place (newest first). `needsSetup` is left alone: it still exempts "finishing the price" from the five hand edits an hour, and saving still clears it.
- A product flagged "needs a price" before arrivals were tracked has no `freshAt` at all: it is treated as new until opened, once. The "pick a product to sell" list is not reordered, and salespeople see no arrival labels or ranking (a salesperson's accept does not stamp `freshAt`).

## Password manager (Android)
- Chrome offers "Save password?" on password boxes. Every other box says `autocomplete="off"`. The PIN asked before something is deleted is a masked text box (`.masked-pin`), not a password box, so it never offers to save.

## Known limits (be honest with yourself about these)
- Identity is phone + PIN with an anonymous Firebase sign-in, so Firestore cannot tell two people apart. Anyone who can reach the
  database and knows a phone number can read that account's profile. The scrambled PIN slows guessing; it does not stop it.
  The real fix is server-side checks (Cloud Functions needs the paid Blaze plan) or Firebase phone sign-in (SMS costs).
- Anything a browser can run can be downloaded. Scrambling the code and App Check make copying slow and useless against your
  database, not impossible.
